# 特性：实盘脚本与设计文档漂移分析工作流（Live Echo Drift Analysis）

## 目的

实盘脚本在迭代中与设计文档、架构文档之间产生偏差（漂移）是常态。如果不加以管理，漂移会逐步侵蚀代码可维护性和行为可预测性。本需求定义一套可重复的漂移分析工作流，让 AI agent 能够按需或按计划执行以下操作：

1. **发现漂移** — 对比实盘脚本当前实现与关联设计文档、架构文档，标注不一致点
2. **分类漂移** — 按严重程度、影响范围、漂移类型（参数漂移/逻辑漂移/结构漂移/文档过时）对每个不一致点进行分类
3. **记录漂移** — 将漂移证据写入结构化报告，留存决策上下文
4. **驱动决策** — 根据分类结果给出处置建议（修复代码 / 更新文档 / 标记接受 / 深入调查）
5. **闭环跟踪** — 跟踪每项漂移从发现到关闭的状态变化

核心关切：漂移不可怕，未被文档化的漂移决定才危险。本工作流不强制代码与设计完全一致，而是要求每个偏差都经过显式决策。

## 范围内

### 对比对象

| 来源 | 目标文件 | 对比维度 |
| --- | --- | --- |
| **运行中实盘脚本** | `scripts/run_live_echo.py` | 代码逻辑、常量、执行路径、API 调用 |
| **关联设计文档** | `docs/design/2026-06-26-live-echo-runner.md` 等 | 策略参数、退出逻辑、风控规则、状态模型 |
| **关联架构文档** | `docs/architecture/` 下相关文件 | 模块边界、数据流、接口契约 |
| **关联计划文档** | `docs/plans/` 下相关文件 | 策略 edge 定义、预期行为、回测基准 |

### 漂移分析维度

| 维度 | 定义 | 识别方法 | 风险倾向 |
| --- | --- | --- | --- |
| **参数漂移** | 代码中常量值与设计文档声明值不一致 | 逐项对比常量定义与文档数值表 | 中低 |
| **逻辑漂移** | 代码实现的控制流、条件判断与设计描述不符 | 追踪关键函数调用路径，对比文档流程 | 高 |
| **结构漂移** | 模块/类的接口、数据流、状态模型与架构图不符 | 对比架构文档中的模块分解与数据流图 | 中高 |
| **文档过时** | 设计文档描述的方案已被代码演进超越 | 检出代码中有但文档未定义的功能或字段 | 中 |

### 漂移严重度分级

| 级别 | 定义 | 处置时限 |
| --- | --- | --- |
| **阻断 (Blocking)** | 漂移导致实际行为与设计预期严重背离，可能引发资金损失或不可恢复状态 | 立即修复 |
| **严重 (Critical)** | 漂移影响策略核心逻辑（退出机制、风控参数），但当前未触发事故 | 下一轮迭代前 |
| **一般 (Normal)** | 漂移是参数调整或行为优化，不影响正确性 | 可排期修复 |
| **提示 (Info)** | 文档未反映最新变更，但不影响行为理解 | 更新文档即可 |
| **已接受 (Accepted)** | 有意识的人为决策导致的偏差，已记录原因 | 无需修复，记录即可 |

### 产出物

| 产出物 | 内容 | 接收者 | 触发条件 |
| --- | --- | --- | --- |
| **漂移检测报告** | 所有发现的不一致点，按严重度排序，含代码证据和文档证据 | 用户（决策用） | 每次执行漂移分析后 |
| **处置决策记录** | 每项漂移的处置决定：修复代码 / 更新文档 / 标记接受 / 深入调查 | 用户（存档用） | 用户做出决策后 |
| **漂移状态看板** | 所有已发现漂移项的跟踪状态：待处置 / 已修复 / 已接受 / 已搁置 | 用户（查阅用） | 按需或周期更新 |
| **漂移历史存档** | 已关闭的漂移项汇总，含原始证据和处置记录 | 归档 | 漂移项关闭时 |

## 范围外

- 策略因子本身的逻辑验证或回测（已有独立验证流程）
- 实盘脚本运行时的实时性能监控
- OKX API 合规性审查（已有独立 code review 流程）
- 自动修复漂移（本工作流仅输出建议，不做自动修复）
- 非本项目的第三方依赖包漂移分析
- 数据库或外部服务的 schema 漂移
- 跨会话漂移分析的增量继续（每次均从头检测）

## 主要用户流程

### 流程 A：按需触发漂移分析

```
用户/定时任务触发漂移分析
    │
    ├─> [Agent] 收集分析素材
    │     ├─ 读取目标脚本：scripts/run_live_echo.py
    │     ├─ 读取关联设计文档：docs/design/ 匹配文件
    │     ├─ 读取关联架构文档：docs/architecture/ 匹配文件
    │     └─ 读取关联计划文档：docs/plans/ 匹配文件
    │
    ├─> [Agent] 逐项对比分析
    │     ├─ 对比 1：常量参数表格 vs 代码常量
    │     │     - 找到所有声明数值，与代码 DEFINE/CONST 逐一比较
    │     ├─ 对比 2：控制流 vs 文档描述
    │     │     - 追踪 main loop / signal execution / exit path
    │     ├─ 对比 3：状态模型 vs 架构文档
    │     │     - 对比 state.json 字段与文档定义
    │     ├─ 对比 4：模块接口 vs 架构契约
    │     │     - 检查函数签名、返回类型、依赖关系
    │     └─ 对比 5：文档未覆盖项
    │           - 检查代码中是否有文档未定义的功能或字段
    │
    ├─> [Agent] 分类标注每项发现
    │     ├─ 标注漂移类型（参数/逻辑/结构/文档过时）
    │     ├─ 标注严重度（阻断/严重/一般/提示/已接受）
    │     └─ 标注证据位置（代码行号 + 文档章节号）
    │
    ├─> [Agent] 输出漂移检测报告
    │     ├─ 报告结构
    │     │     ├─ 总览：漂移项数、严重度分布、分析耗时
    │     │     ├─ 漂移清单：按严重度降序排列
    │     │     ├─ 每项详情：[漂移描述 | 代码证据 | 文档证据 | 类型 | 严重度 | 建议处置]
    │     │     └─ 附录：分析覆盖范围声明（哪些文件覆盖了、哪些未覆盖）
    │     │
    │     └─ Agent 不得生成模糊描述，每项漂移必须有明确引用
    │
    └─> [用户] 审查报告并做出决策
          ├─ 修复代码 → 漂移以代码为准，后续更新文档对齐
          ├─ 更新文档 → 设计文档对齐代码，视为技术债务
          ├─ 标记接受 → 记录原因，该漂移转为 Accepted 并结案
          └─ 深入调查 → Agent 补充分析，下一轮再决策
```

### 流程 B：周期性漂移检查

```
定时调度（如每双周/每迭代结束）
    │
    ├─> 检查自上次分析以来，目标脚本是否有变更
    │     ├─ 无变更 → 跳过本轮，输出"无变更，漂移状态不变"
    │     └─ 有变更 → 执行流程 A
    │
    └─> 检查关联文档是否有版本更新
          ├─ 有更新 → 标记"设计基线已更新"，执行流程 A
          └─ 无更新 → 无操作
```

### 流程 C：漂移状态跟踪和关闭

```
用户做出处置决策后
    │
    ├─> 记录处置决策到漂移状态看板
    │     ├─ 待处置 / 已修复 / 已接受 / 已搁置
    │     ├─ 决策时间、决策人
    │     └─ 备注（接受原因、搁置理由、修复参考）
    │
    ├─> 已修复漂移 → 下一轮漂移分析中验证是否确实修复
    ├─> 已接受漂移 → 关闭，原因须明确记录
    ├─> 已搁置漂移 → 保留在待关闭状态，定期提醒
    └─> 关闭的漂移 → 移入漂移历史存档
```

## 业务规则

### 触发规则

- 用户可随时手动触发漂移分析
- 目标脚本发生重大变更（修改行数 > 50 行或修改涉及核心逻辑）后，建议触发一次
- 周期性检查频率：每双周一次，或每个迭代结束时
- 以下事件建议立即触发：实盘行为异常、产生非预期亏损、脚本 crash 后恢复

### 分析规则

- 每项漂移必须同时提供代码证据（文件 + 行号）和文档证据（文件 + 章节）
- 无法提供代码证据或文档证据的漂移项不得列入报告
- Agent 归因不确定时，标注置信度（高/中/低），并列出其他可能解释
- 同一漂移在同一基线对比中只报告一次，不得重复
- 上一轮已记录但本轮未修复的漂移，本轮必须复现引用

### 分类规则

- 参数漂移中超出设计值 ±20% 的自动标为"严重"以上
- 逻辑漂移中涉及退出机制、风控条件的自动标为"阻断"或"严重"
- 架构漂移中涉及模块边界和接口契约的至少标为"一般"
- 文档过时导致的漂移标注为"提示"

### 决策规则

- 阻断项必须给出明确的修复或回退建议
- 严重项必须给出至少一种处置方案
- Agent 不得自动修复漂移，只能输出建议
- 标记为"已接受"的漂移必须记录人为决策原因，格式固定：`ACCEPTED: <reason>`
- 同一漂移被两次标记"已接受"而未修复的，第三轮自动升级为"严重"

### 数据保留

- 漂移检测报告保留 180 天
- 漂移状态看板保留至所有项目关闭
- 漂移历史存档永久保留

## 角色与权限

| 角色 | 职责 | 权限 |
| --- | --- | --- |
| **漂移分析 Agent** | 收集素材、执行对比、分类标注、输出报告 | 读取代码、读取文档、输出报告 |
| **用户（决策者）** | 审查报告、做出处置决策、执行修复或文档更新 | 读取报告、修改代码、修改文档、标记漂移状态 |
| **维护人（可选）** | 在用户无暇时处理提示/一般级别的漂移 | 读取报告、修改文档（不修改代码） |

### 权限边界

- Agent：只读 + 分析 + 建议
- 用户：读写 + 决策 + 执行
- 维护人：只读 + 建议 + 文档变更

## 边缘情况

### 素材相关

- **目标脚本已被删除或重命名** — Agent 需报告"目标不存在"并终止分析，而非报错崩溃
- **关联文档不存在或已被归档** — Agent 需标注"无设计文档可对比"，仅做代码结构分析
- **多版本文档冲突** — 存在多个版本的设计文档时，Agent 需声明以最新版本为准，并在报告中注明
- **文档引用模糊** — 文档描述笼统导致无法精确定位对比点时，Agent 需标注"文档模糊，无法精确对比"
- **文件编码异常** — 脚本或文档包含非 UTF-8 编码时，Agent 需尝试解码并标记可疑行

### 分析过程相关

- **脚本运行中产生竞态** — 分析期间脚本在运行，state.json 可能处于中间状态，Agent 需忽略运行时状态，只对比静态结构
- **发现漂移项过多（> 20 项）** — Agent 需自动停用 Info 级漂移的输出，先呈现 Blocking + Critical 项，引导用户按优先级处理
- **跨文件间接漂移** — 实盘脚本调用了工具模块（如 `utils.py`），但工具模块返回结果与设计不符，Agent 需追溯调用链而不能只查调用处
- **漂移重复报告** — 本轮漂移与上轮完全相同的，需在报告中标注"与上轮一致，未修复"

### 决策相关

- **用户全部标记为"已接受"** — Agent 需提示风险累计，建议至少修复 Blocking 项，并在报告中标注"用户接受所有漂移"
- **用户要求 Agent 自动修复** — Agent 应拒绝，重申本工作流边界（仅输出建议，不自动修改）
- **长时间无决策** — 漂移检测报告发出后 7 天未收到决策的，Agent 需自动触发一次提醒
- **文档或代码在分析后立即变更** — 漂移分析结论可能已过时，Agent 需提示用户重新运行分析

## 未解决问题

### 通用问题

- **对比基线锁定** — 漂移分析以哪个版本的文档为基线？以最新 commit 为准，还是以正式 release 版本为准？
- **增量分析** — 跨会话做增量漂移分析（只分析变更部分）还是每次全量对比？当前定为全量，后续可根据成本考虑增量方案。
- **报告存储位置** — 漂移检测报告输出到 `docs/reports/` 目录，但命名规则尚未标准化。
- **漂移状态看板实现** — 当前计划用 Markdown 文件维护状态，能否支撑长期跟踪？

### 分析精度

- **参数对比精度** — 设计文档中数值写为 `$7` 但代码中是浮点值，字符串格式不同时如何自动识别匹配？
- **逻辑描述解析** — 设计文档中的流程语言（自然语言）如何可靠地与代码控制流建立对应关系？
- **漂移自动检出率** — LLM 驱动的对比分析可能会有漏检，目前接受非 100% 检出率，重点是关键漂移不遗漏。

### 决策跟踪

- **漂移状态看板格式** — 用 Markdown 表格维护还是引入轻量 issue 跟踪？
- **决策提醒方式** — 超时提醒用控制台日志还是其他通知渠道？
- **搁置漂移的复审周期** — 搁置漂移应该多久被拉回审查一次？建议每月。

## 验收准则

### 漂移检测

- [ ] Agent 能根据指定脚本路径自动找到关联的设计文档和架构文档
- [ ] Agent 能正确识别参数漂移（常量数值与文档不一致）
- [ ] Agent 能正确识别逻辑漂移（退出机制、风控条件与文档不一致）
- [ ] Agent 能正确识别文档过时（代码中有但文档中未定义的字段或功能）
- [ ] 每项漂移都有明确的代码证据（文件名 + 行号范围）
- [ ] 每项漂移都有明确的文档证据（文件名 + 章节号）
- [ ] 漂移检测报告按严重度降序排列，结构清晰

### 漂移分类

- [ ] Agent 能按漂移类型（参数/逻辑/结构/文档过时）正确分类
- [ ] Agent 能按严重度（阻断/严重/一般/提示/已接受）正确分级
- [ ] 分类规则（±20% 自动严重、退出机制自动阻断等）被正确执行
- [ ] Agent 对自己的判断标注置信度（高/中/低）

### 处置决策

- [ ] 阻断项有明确的处置建议
- [ ] 严重项有至少一种处置方案
- [ ] Agent 不会自动修改代码或文档
- [ ] 用户决策能正确记录到漂移状态看板
- [ ] "已接受"漂移的记录格式满足 `ACCEPTED: <reason>` 要求

### 闭环验证

- [ ] 至少完成一轮完整的"触发分析 → 输出报告 → 用户决策 → 状态更新"闭环
- [ ] 漂移检测在同一基线下的重复执行结果保持稳定（不随 LLM 输出波动）
- [ ] 漂移历史存档可被查阅
- [ ] 脚本无变更时跳过分析（输出"无变更"摘要）
- [ ] 目标脚本不存在时优雅终止，非崩溃

### 实施就绪门禁

以下条件全部满足时，本需求被视为"实施就绪"：

- [ ] 范围内的行为已足够具体，开发人员无需猜测即可构建用户可见行为
- [ ] 非目标被明确列出
- [ ] 已描述主要用户流程（按需触发 + 周期性检查 + 状态跟踪三个流程）
- [ ] 角色与权限已被覆盖（漂移分析 Agent / 用户 / 可选维护人）
- [ ] 数据/模型影响已被覆盖：产出物（漂移报告、决策记录、状态看板、历史存档）的格式和保留策略已定义
- [ ] API/集成影响已被覆盖：分析过程无外部 API 调用，仅涉及文件系统读写
- [ ] 空态、加载态、错误态与权限拒绝态已被覆盖：目标不存在、文档缺失、分析过多漂移、用户无决策等
- [ ] 验收准则具备可测试性
- [ ] 开放性问题要么不阻断实施，要么已明确标注会阻断实施
