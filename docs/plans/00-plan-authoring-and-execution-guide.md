# 计划编写与执行指南

## 目标

`docs/plans/` 用于需要明确范围、关闭标准和证明的非平凡执行切片。

## 何时编写计划

当任务符合以下情况时，编写计划：

- 更改 API、数据库/模型、认证、集成、部署或公共契约行为
- 在多个功能表面上更改用户可见行为
- 涉及多个模块并更改共享行为
- 预计需要多个 AI 会话
- 修改超过 5 个文件或可能超过约 200 行更改
- 需要分阶段实施或在关闭前需要明确证明

## 计划决策表

| 范围 | 计划级别 | 审计规则 | 示例 |
| ----------------------------------------------------------------------------------------------------------------------------------- | ---------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 琐碎的本地编辑 | 无需计划 | 无需草稿审查 | 拼写/文案更改、单一样式调整、仅测试清理 |
| 非平凡的跟踪工作 | 完整计划 | 需要独立草稿审查和独立关闭审计 | 带有文档/测试更新的小型 UI 优化、具有清晰现有测试的简单本地错误修复 |
| 契约、数据/模型、API、认证、权限、集成、部署、跨表面、过时文档冲突或明显高风险范围 | 完整计划 | 需要独立草稿审查和独立关闭审计 | 结账流程、登录行为、数据迁移、外部 Webhook、多模块重构 |

如果不确定，使用完整计划。

## 最低规则

1. **从实时基线开始。** 先阅读仓库，然后编写 `Current Baseline`。不要依赖记忆或旧计划。对于全新功能，基线必须清点功能将触及或矛盾的所有现有代码——硬编码值、缺失的钩子、不兼容的模式。清点不是可选的。
2. **编写目标和非目标。** 如果其中任何一个不清楚，计划边界就没有准备好。
3. **使用复选框进行执行和关闭。** 未选中的项目意味着直到关闭前都未完成的工作。
4. **一个计划，一个结果表面。** 如果计划需要多个独立的关闭标准，它太宽泛了。拆分它。共享相同行为契约和关闭标准的多模块提取或迁移仍然是一个结果表面——不要过度拆分。
5. **关闭前提供证明。** 在仓库包含每个退出标准的可验证证明之前，不要将计划标记为完成。
6. **不要进行代码设计转储。** 计划捕获范围、证明和关闭逻辑，而不是低级实现细节。例外：重构和提取计划必须包括提取模块之间的接口契约——这些是结构性边界定义，不是实现伪代码。
7. **用类型标记项目。** 每个执行项目必须是 `Fix`、`Add`、`Decision`、`Proof` 或 `Follow-up`。`Fix` 涵盖缺陷修复；`Add` 涵盖全新代码或配置。一个项目可以携带多个类型（例如 `Decision | Add`）；当它这样做时，所有隐含的责任都适用。已确认的现场缺陷或契约漂移必须是 `Fix`，而不是 `Follow-up`。当一个阶段中 80% 以上的项目共享一个类型时，在阶段级别声明统一类型而不是每个项目（例如 `Phase 1 — Fix-heavy (8/10 items tagged Fix)`）。
8. **有意识地记录技能使用。** 对于每个可重用技能重要的阶段或项目，记录 `Skill: <name>` 或 `Skill: none`。技能选择工作方法，而不是业务事实。如果命名了技能，其所需输入和预期输出必须从 `docs/skills/README.md` 和引用的所有者文档中已经清楚。
9. **用理由记录决策。** 每个 `Decision` 项目必须记录选择、考虑的替代方案以及任何残余风险。将理由写入计划或引用的文档。如果决策在承诺之前需要原型设计或探索，添加一个临时的 `Explore` 项目，该项目必须在 `Decision` 解决之前结束。框架强制或明显的选择（例如"必须符合现有框架模式"）可以标记为受约束，而无需完整的替代方案分析。
10. **关闭前检查清单完整性。** 在将计划标记为完成之前，范围内的检查清单项目不得保持未选中状态。要么完成它，要么用书面理由明确将其移出范围。计划批准后的范围缩小是范围变更，必须记录理由；悄悄从范围中删除项目是违规行为。
11. **关闭前文本一致性。** 在关闭之前，验证 `Plan Status`、每个阶段的 `Status`、每个阶段的 `Exit Criteria`、`Closure Gates` 和 `docs/logs/` 条目是否全部一致。当内部阶段仍显示 `draft` 时，顶部不能显示 `completed`。
12. **独立草稿审查和关闭审计。** 在独立草稿审查将创建的计划修订为可接受的执行契约之前，不要实施它，也不要因为完成最后一个实施切片而将其标记为完成。使用单独的审查流程。关闭审计必须由独立的子代理或审查员执行；自我审查不能将创建的计划标记为完成。受保护区域、未解决的产品风险和真相来源冲突需要人工/子代理审查或保持开放。
13. **不可降级项目** 不能降级为非阻塞跟进：已确认的现场缺陷、已确认的契约漂移、已确认的所有者文档漂移以及仓库中已修复的 CI/lint 规则。

## 计划状态流程

有意识地使用这些状态：

- `draft` - 计划存在但尚未通过独立草稿审查
- `active` - 独立草稿审查已达成可接受的执行契约，可以开始实施
- `completed` - 独立关闭审计接受关闭
- `superseded | replaced | deferred | cancelled` - 当计划不再以其原始形式拥有实时关闭时使用

创建计划的推荐默认流程：

1. 将第一个诚实的草稿创建为 `draft`
2. 运行独立草稿审查直到草稿可接受
3. 在 `## Draft Review Record` 中记录迭代
4. 将 `Plan Status` 更改为 `active`
5. 执行并更新阶段/工作流状态
6. 仅在独立关闭审计后关闭

### 反懈怠规则

关闭前的每个范围内项目必须恰好落在一种状态：`landed`、`adjudicated as residual-risk-only`、`moved to explicit successor ownership` 或 `removed from scope with recorded reason`。

以下词语在范围内项目中禁止使用：`optional`、`if time permits`、`consider`、`maybe`、`nice to have`、`as needed`。如果某个项目确实是可选的，明确将其移出范围，而不是让其处于模糊状态。

`Follow-up` 项目必须命名将其提升到范围内的触发条件（例如"当用户数量超过 10K 时"）。`Deferred But Adjudicated` 项目必须命名将重新打开它的事件或决策（例如"如果采用新 API，这项工作可能变得多余"）。

## 执行时

1. 在实施之前，直接修订计划直到独立草稿审查发现没有阻塞问题，然后默认将草稿审查证据永久记录在计划中。
2. 在草稿审查期间将新计划保持在 `Plan Status: draft`。仅在草稿审查记录显示计划可执行后更改为 `active`。
3. 当您开始一个切片时，将其 `Status` 更新为 `in progress`。
4. 当您完成一个切片时，将其 `Status` 更新为 `completed` 并勾选所有执行项目和退出标准。
5. 在执行阶段之前，确认列出的 `Skill` 仍然与任务和可用输入匹配。如果不匹配，在继续之前更新计划。
6. 如果切片更改实时基线或公共契约，其退出标准必须包括文档更新步骤。如果不需要文档更新，明确写 `No owner-doc update required`。
7. 不要因为函数签名存在就将切片标记为完成。验证行为、错误处理和测试覆盖也已落地。
8. 如果某个项目无法完成，将其移至 `Deferred But Adjudicated` 并注明分类和原因。不要让它在执行列表中保持未选中状态。
9. 保持 `docs/logs/` 与计划进度同步。当所有阶段在一个冲刺中涵盖相同功能时，计划关闭时的单个聚合日志条目就足够了；仅当阶段跨越不同日期或不同可交付成果时才需要单独的阶段性条目。

## 关闭时

在设置 `Plan Status: completed` 之前，执行以下所有操作：

**所有创建的计划：**

1. 检查每个阶段的 `Exit Criteria` —— 每个都必须是 `[x]`。
2. 检查每个 `Closure Gates` 项目 —— 每个都必须是 `[x]`。
3. 验证文本一致性：顶部状态、阶段状态、退出标准、关闭门和日志条目全部一致。
4. 区分"接口存在"和"行为完成"。用测试或演示验证实际运行时行为，而不仅仅是类型签名。
5. 运行仓库的真实验证命令。对于主要结果表面是视觉、行为或 UX 驱动的计划，在计划中自定义验证门并明确说明理由。
6. 由独立的子代理或审查员执行独立关闭审计。
7. 如果计划使用了单独冷重播回退（参见 `AGENTS.md` Reviewer-Availability Fallback），关闭记录必须说明已使用，并确认针对计划、受影响的文档、实际差异和真实验证命令执行了冷重播自检。

**完整关闭**（多会话、多模块或高风险计划 —— 添加这些）：

7. 从头到尾重新阅读整个计划，而不仅仅是最新的切片。
8. 在计划的 `Closure` 部分记录独立关闭审计证据，并在存在时链接 `docs/audits/` 下存储的任何审计文件。

如果其中有任何项目未完成，将其移至 `Deferred But Adjudicated` 并注明分类和原因。不要让它在执行列表中保持未选中状态。
