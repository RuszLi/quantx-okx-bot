### 背景回顾

V3 Phase 0 回测覆盖 7 个 edge（A/B/C/D/E/K/H），汇总报告详见 `reports/v3_output/v3_phase0_combo.md`。硬约束（§18.4）要求「A 或 E 至少 1 条 PASS + 至少 2 条 strategy 单独 PASS」。A/E 均 ABORT，导致 ensemble 无法进入 Day 3。

### 问题一：为什么 edge A（listing_fade）不产生任何收益？

#### 根因：OKX API 数据深度不足，非策略逻辑问题

`event_failure_reasons.json` 记录了详细原因：

| 失败原因 | 数量 | 含义 |
|:---|:---:|:---|
| `older_than_7d_okx_limit` | 24 | 事件发生时间超过 7 天，OKX 公开 API 不提供 1m kline 历史数据 |
| `window_too_short` | 11 | 事件在 7 天内，但信号计算所需的数据窗口不够长 |
| `ValueError` | 7 | 数据处理异常 |
| **可回测事件** | **0** | |

**结论：** 42 个上币事件中，0 个具备完整的回测数据条件。这不是策略逻辑无效，而是**底层数据基建问题**。

#### 衍生追问：window_too_short 是否需要关注？

18 个 7 天内的事件全部处理失败（7 ValueError + 11 window_too_short），说明 strategy 的信号计算窗口 > 7 天级别。如果该策略需要 7+ 天的 kline 数据才能产生信号，那么即便解决了 OKX 数据深度问题，window_too_short 也可能在实盘中持续发生（新上币本就没有历史数据）。这是一个需要回看策略设计的点——是否可能缩短所需窗口，或切换 tick 级别数据。

### 问题二：为什么 edge C（beta_decouple）和 edge D（weekend_wick）的胜率接近 92-93%？是否正常？

#### 数据概览

| 指标 | C (beta_decouple) | D (weekend_wick) | 对比：K (pair_mr) | 对比：B (funding_extreme) |
|:---|:---:|:---:|:---:|:---:|
| 交易笔数 | 525 | 142 | 2,098 | 238 |
| 胜率 | 91.62% | 92.96% | 51.29% | 4.62% |
| ev_R | 0.3442 | 1.1644 | -0.3195 | -0.3129 |
| Profit Factor | 51.81 | 48.22 | 0.39 | 0.01 |
| 最大回撤 | 98.14% | 94.36% | 99.97% | 84.92% |
| 最大连续亏损 | 2 | 1 | 19 | 98 |
| 最大连续盈利 | 46 | 39 | 13 | 1 |
| 鲁棒性 | HIGH (27/27) | HIGH (27/27) | — | — |

#### 交易笔数分析

C 的 525 笔在 27 组参数下保持恒定（`sensitivity_grid.csv` 可见 `n_trades` 始终为 525），说明 **入场逻辑是确定性的**——参数变化不影响开仓时机，仅影响退出的损/费/滑点模拟。这是健康的信号，说明没有「参数挖掘」式的过拟合。相对于 K 的 2,098 笔，C/D 的交易频率与其策略定位相符：
- **beta_decouple**：捕捉资产与市场相关性脱钩后的均值回归，信号密度与行情波动正相关，525 笔合理
- **weekend_wick**：专门捕捉周末→周一开盘的影线修复，天然低频，142 笔符合预期

#### 胜率分析：高胜率的可能解释

**支持「真实结构性 edge」的证据：**

1. **参数鲁棒性极强**：27/27 组合全部 PASS，且 win_rate 随 fee/slippage 增加**单调递减**（C: 0.9543→0.8686，D: 0.9366→0.9085），这是真实 edge 的典型特征——edge 被摩擦成本侵蚀但不消失，而非过拟合后的突然崩塌。

2. **退出原因分布合理**：
   - C：474 TIME（90%）、51 TP（10%）、0 SL。大多数单子**持有到期退出**而非触止盈，说明 edge 是「时间衰减型」而非「方向预测型」。
   - D：97 TP（68%）、44 TIME（31%）、1 SL（1%）。以止盈为主，符合「影线填充 → 回归均值」的微观结构逻辑。

3. **胜率高 ≠ 无风险**：C 的 max_drawdown_pct 高达 98.14%，D 为 94.36%。这意味着策略在**绝大多数时间小赚，但少数几次亏损几乎清空账户**。这是典型的高胜率/低盈亏比（或右偏收益分布）策略特征。

**需要警惕的信号：**

4. **max_consec_losses = 2 / 1**：对任何交易策略而言都异常低。连续亏损次数过少意味着策略从未经历过「与自己逻辑相悖的市场状态」。这可能是因为回测窗口正处于一个特别有利于该策略的市场阶段（regime dependency）。

5. **avg_holding_bars = 0.0**：525 笔和 142 笔交易的持仓时长均为 0 bar，这**很可能是回测框架的 bug 或数据记录问题**——即使是最快的 tick 级交易也有持仓时长。需排查回测引擎的 dataclass 初始化或持久化逻辑。

6. **最大连续盈利 46 / 39**：几乎完全一边倒的运行结果，统计学上较为罕见，可能暗示：
   - 回测窗口处于特定的市场 regime（如持续低波动趋势）
   - 或策略对某些 symbol 有结构性偏好（需要查看 `group_by_symbol.csv`）
   - 或存在未被发现的逻辑 bug（如信号计算中意外引用了未来数据）

#### 结论：胜率是否「正常」

**胜率本身不反常**，一些真实存在的市场微观结构 edge（如做市、套利、影线修复）天然具备高胜率特征。但配合以下指标需要谨慎解读：

1. **94-98% 的回撤**使得策略不具备单独部署的稳健性——这是真正的风险所在
2. **avg_holding_bars = 0.0** 必须修复后再做判断
3. **回测窗口是否覆盖了至少一个完整的市场 regime 周期？（如牛市→熊市→震荡）** 需要确认回测数据的时间范围
4. 建议补充 `group_by_symbol.csv` 分析——查看是否为少数几个 symbol 贡献了大部分盈利

#### 后续建议

- [ ] 修复 avg_holding_bars 上报 bug，确认持仓时长数据
- [ ] 补充回测时间范围说明，确认是否覆盖完整市场周期
- [ ] 查看 C/D 的 `group_by_symbol.csv`，检查盈利是否集中在少数 symbol 上
- [ ] 对 C/D 做 out-of-sample（OOS）测试，验证胜率在未见过的时段是否保持
- [ ] 关注 max_drawdown 的问题——即使 ensemble 组合也难以承受 94%+ 的单策略回撤

### 问题三：edge A 的 window_too_short——是否可能缩短所需窗口或切换数据源？

> 核心矛盾：新上币（new listing）天然没有历史数据，`window_too_short` 在回测和实盘中都会发生。是否可能通过缩短计算窗口或切换 tick 级数据来解决？

#### 当前 window 需求的精确分析

从 `src/backtest/strategies/listing_fade.py` 看，信号计算流程：

| 步骤 | 所需 bar 数 | 条件 |
|:---|:---:|:---|
| pump 检测 (`market_data.iloc[:5]`) | 5 bars | 首 5 根 1m kline 中最高价 / 开盘价 ≥ 1.15 |
| 回撤检测 (`range(5, len(market_data))`) | ≥ 1 bar (bar 5+) | 价格回落到 pump_high 的 85-88% + 成交量 ≤ 均值 50% |
| 退出 (`pullback_idx + 5`) | 最多 5 bars | TIME 退出，紧缩到剩余数据末尾 |
| **外层 guard** (`len(window) < 6`) | **6 bars** | 回测框架 `run_listing_fade_strategy` 线 550 |

**结论：信号产生的绝对下限是 6 根 1m bar（约 6 分钟），但为了给回撤检测留空间，合理期望是 ~10-15 bars。**

#### window_too_short 根因调查

18 个 7 天内的事件：11 个 window_too_short + 7 个 ValueError。

11 个 window_too_short 的含义是——
**下载函数确实返回了 kline 数据（否则会标记为 empty_klines），但 listing 时间后 60 分钟内不足 6 根 bar。** 最可能的原因是这些 listing 发生在脚本运行前几分钟内，OKX 的 kline 缓存尚未积累到 6 根。

这不是「数据深度不够」，而是 **「listing 过于新鲜，API 还来不及返回足够 bars」**——这是事件驱动回测脚本一次性扫描所有事件时的特有现象。如果换成实时的流式处理，随着时间推移数据会自动补全。

#### 方案评估

| 方案 | 可行性 | 效果 | 代价 |
|:---|:---:|:---|:---|
| **A. 将 60-min 窗口缩短为 15-min** | ✅ 简单 | 减少数据下载量，但不解决 window_too_short（< 6 bars） | 低，只需改一行常量 |
| **B. 将 `len(window) < 6` 降为 `len(window) < 3`** | ⚠️ 需要验证 | 可释放部分因「listing 太新」被拦截的事件；但 signal 可能不可靠（pump 检测需要 5 bars） | pump 只用了前 5 bars，如果数据不到 5 bars 则 `iloc[:5]` 取不到完整数据 |
| **C. 事件重试机制** | ✅ 推荐 | 对 window_too_short 的事件，下次运行脚本时重试（数据已积累） | 需要修改回测循环增加状态缓存 |
| **D. 切换 tick 级数据** | ❌ 不可行 | — | OKX 公开 API 不提供 tick 级历史数据；策略逻辑基于 OHLC 形态，重写为 tick 级别相当于重写策略 |
| **E. 改用其他交易所数据源** | ⚠️ 依赖外部 | Binance 的 listing 事件 + 1m kline 可能有更深度历史（跨所松绑 §13.1 已允许） | 需确认 Binance 新合约的 1m 历史深度；Binance 和 OKX 的上币事件不完全重合 |
| **F. 回测时仅依赖「7 天内且有足够数据」的事件** | ✅ 现状已实现 | 24 个旧事件跳过，11 个太新事件跳过，实际 0 条可回测 | 当前的 ABORT 决策是正确的，但不意味着策略无效 |

#### 推荐方案

1. **短期（回测）**：接受现状。24 个事件超出 7 天是 OKX API 的硬约束，无法绕过。11 个 window_too_short 本质是「数据成熟度滞后」，对回测结论影响有限。

2. **中期（回测改进）**：对 window_too_short 事件**加入重试标记**，在多次回测运行中自动重试，等待数据成熟。这样至少能释放部分被误杀的事件。

3. **长期（实盘准备）**：
   - listing_fade 是事件驱动策略，**天然适合实盘**——订阅 OKX websocket 获取新上币通知，实时收集 1m kline，5-10 分钟后即可产生信号
   - 实盘中 `window_too_short` 不会发生（数据实时积累，策略按需等待）
   - **实盘无需做任何窗口缩短或数据源切换**，当前策略逻辑直接可用

4. **策略级改进（可选）**：如果希望信号更早触发（listing 后 3-5 分钟内），可以：
   - 把 pump 窗口从 5 bars 压缩到 3 bars（降低 pump 门槛，增加误报风险）
   - 但当前 5 bar 窗口在实盘中等 5 分钟就能满足，意义不大

#### 最终判定

| 维度 | 结论 |
|:---|:---|
| window_too_short 的本质 | 批量回测脚本的时间性假象，非策略逻辑缺陷 |
| 实盘影响 | **无影响**——实时数据自然积累，不会触发 window_too_short |
| 是否需要缩短窗口 | **不需要**——当前 5 bars pump + ~10 bars 总需求在实盘中等 5-10 分钟即可满足 |
| 是否需要切换 tick 数据 | **不需要**——迁移成本高，收益为零 |
| 真正应做的事 | 等待 OKX kline 深度自然积累，或在相近时间窗口内重复回测 |

**结论：edge A 的策略逻辑在当前设计中是可行的。回测得 0 笔是因为 OKX API 的 7 天深度上线与批量回测的时间性冲突，不是策略本身的问题。实盘中 listing_fade 可以正常运行。**
