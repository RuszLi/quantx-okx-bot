## 澄清记录（2026-06-29）

> 以下结论基于代码证据逐条澄清，原始问题见上一节「待澄清问题」。所有引用行号已由 AI 二次核实，与当前代码一致。

### 1. funding 家族 n_trades=0 根因

**主因是数据获取缺陷，不是参数空间或信号定义。**

证据链（行号均已核实）：

- `scripts/run_edge_discovery_pipeline.py` 的 `_load_market_bundle` 调用 `src.pipeline.data_layer.get_funding("BTC-USDT-SWAP", start, end)`，期望拿到训练窗口（默认 2024-01-01 至 2025-01-01）的完整 funding 历史。
- `get_funding` 内部调用 `_okx_funding(symbol, limit=200)`（[`data_layer.py:210`](../../src/pipeline/data_layer.py#L210)）。
- `_okx_funding` 调用 `src.data.okx_funding.fetch_funding_history(inst_id, limit=limit)`。
- `fetch_funding_history` 直接调用 OKX API `funding_rate_history`，**只传 `limit`，不传 `start/end`，也没有分页逻辑**（[`okx_funding.py:18`](../../src/data/okx_funding.py#L18)）。
- OKX 该接口默认 limit=100，返回的是**最近的 100 条 funding 记录**。
- BTCUSDT SWAP 每 8 小时结算一次，100 条 ≈ 33 天数据。
- 训练窗口为 365 天，意味着其余约 332 天的 `funding_rate` 被 `ffill().fillna(0.0)` 填充为 0（[`run_edge_discovery_pipeline.py:183`](../../scripts/run_edge_discovery_pipeline.py#L183)）。
- 当 `funding_rate` 长期为 0 时：`funding_mean` ≈ 0、`funding_std` ≈ 0、`funding_z = (0-0)/0` 为 NaN 或异常值、`abs(funding_z) < z_score_threshold`，无信号。
- 最终 `compute_signals` 返回空 DataFrame，`executor.run_candidate` 走空分支，`n_trades=0`。

**次要因素：** `rv_window` 3/4/6 小时 + `funding_window` 480/720/960 小时（20-40 天）warm-up 消耗大；策略 universe 仅 BTCUSDT，信号本来就稀疏。但即便参数再宽松，只要 funding 数据大面积为 0，信号仍无法生成。

**结论：必须在推进多家族前先做根因修复。** 这不是 funding 策略无效，而是数据层没有按时间窗口分页获取历史数据。如果不先修复，同样的问题会复制到任何依赖历史 API 数据的新家族（OI、liquidation 虽然用本地缓存，但 orderbook 和其他外部数据源也会遇到类似分页/窗口问题）。

**建议动作：** 修复 `get_funding` / `fetch_funding_history` 支持按 `start/end` 分页拉取，或复用 V3 编排器已有的本地 funding parquet 缓存机制（[`scripts/run_v3_phase0_backtest.py:92`](../../scripts/run_v3_phase0_backtest.py#L92) 的 `load_funding_history` 带 `FUNDING_CACHE`），然后重新跑 funding 族 full-run，确认到底是数据问题还是策略本身无 edge。

### 2. 多家族优先级

按「数据可得性 + 实现成本 + 期望 alpha + 与 funding 失败模式的差异化」排序：

| 优先级 | 家族          | 数据状态                                                  | 实现成本                          | 与 funding 差异化                               | 建议 |
| ------ | ------------- | --------------------------------------------------------- | --------------------------------- | ----------------------------------------------- | ---- |
| 1      | `liquidation` | `get_liquidations` 已实现（[`data_layer.py:326`](../../src/pipeline/data_layer.py#L326)） | 低（只需写 generator）            | 事件驱动、微观结构、与 funding 均值回归逻辑不同 | 先做 |
| 2      | `oi`          | `get_open_interest` 已实现（[`data_layer.py:256`](../../src/pipeline/data_layer.py#L256)） | 低                                | 未平仓量 vs 资金费率，相关但独立                | 其次 |
| 3      | `calendar`    | 无需新数据                                                | 最低                              | 日历效应，alpha 可能较弱                        | 第三 |
| 4      | `orderbook`   | `get_order_book_snapshot` 是 stub（[`data_layer.py:304`](../../src/pipeline/data_layer.py#L304)） | 最高（需新建数据摄取/存储）       | 微观结构，与 funding 完全不同                   | 最后 |

**理由：**

- `liquidation` 和 `oi` 的数据层已经接通，只需补 generator，最快出结果。
- `liquidation` 与 funding 的失败模式差异最大：funding 是连续均值回归信号，liquidation 是事件驱动的 fade/cascade 信号，如果 funding 族因为数据 bug 导致全灭，liquidation 仍可能独立有效。
- `calendar` 虽然实现最简单，但 alpha 来源弱，且 `funding_time_proximity` 与 funding 族有一定重叠。
- `orderbook` 必须等数据基础设施就绪，否则无法运行。

### 3. order book 历史数据存储

**必须先评估压缩/降采样方案，再启动 orderbook 族。**

当前 `get_order_book_snapshot` 直接返回 `None`，没有任何数据摄取逻辑。OKX order book 快照如果是全量 L2，1 分钟一条 BTC 可能几百 KB 到数 MB，一年数据会非常大。按 Risk Register F3，这是已知风险。

**建议在 Phase 7 方案中专门开辟一节：**

- 评估 Parquet + zstd 压缩。
- 评估只存储 top N 档位（如 top 5/10/20）而非全量 L2。
- 评估降采样（如每 5 分钟或事件触发采样）。
- 评估本地存储预算和回放性能。

**orderbook 族应等这一节方案确定后再开发。**

### 4. calendar 族数据契约

**不需要新增 data_layer 接口。**

`calendar` 族当前声明的 `required_data_fields=["klines", "funding_rate"]`（[`families.py:79`](../../src/pipeline/families.py#L79)，CALENDAR_FAMILY 定义）已经够用：

- `day_of_week`、`month` 可直接从 klines 索引推导。
- `funding_time_proximity` 可从 `funding_rate` 的 `next_funding_time` 推导（[`data_layer.py:230`](../../src/pipeline/data_layer.py#L230) 已计算该列）。
- 无需新增 `get_calendar_events()` 之类的接口，除非后续要接入外部宏观日历（如美联储决议、CPI 发布），那是扩展项，不是 Phase 7 必须。

**建议：** generator 内部从输入 bundle 的索引和已有列推导 calendar 特征，保持 data_layer 接口不变。
